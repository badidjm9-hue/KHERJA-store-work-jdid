# Phase 2: one Kherja app, two role-based interfaces

Status: complete, awaiting review. Cutover (`/` and `/driver` → shell) is NOT done and needs separate approval.

## What was built
- `app/kherja.html` (generated by `node app/build-shell.js` from `app/shell/*` plus the CSS/sprite/logo of `app/index.html`). Served at `/app` and `/app/driver` (preview routes; two lines added to the `PAGES` map in `backend/server.js`).
- One shell: shared theme bootstrap, i18n/RTL, tokens, sprite, toast, shared gate (language → phone → OTP, written once), role resolver, notice screen.
- Two role views kept as inert `<template>`s + inert `text/plain` code blocks. Only the view for the role the server returns is instantiated; the other never runs. Views are the existing passenger and driver code with their own login screens removed.
- Legacy `/`, `/driver`, `/admin` and every legacy file are byte-identical to Phase 1 (verified in `e2e/shell.test.js`, "routes").

## Role rules (as implemented)
1. Launch: `GET /api/me`. 200 → mount the view for `role` (`rider` → Passenger, `driver` → Driver). 401 → gate. Anything else → notice with Retry (no logout).
2. After login: the view is chosen from the `role` in the `verify` response, never from the picker or the URL.
3. The Passenger/Driver picker is sent as `role` only on `verify`; the backend honours it only when it creates the account. Existing accounts keep their stored role (proved in `backend/roles.test.js`).
4. URL path (`/app` vs `/app/driver`) only chooses the first gate screen and the picker default.
5. `admin` accounts get a notice, no mobile interface. `/admin` (cookie `asid`, password login) is untouched; a mobile `sid` session does not open any admin API.
6. No role switching: no switcher exists. `/api/dev/role` is never called. `window.Kherja` is frozen. Nothing is read from localStorage except the pre-existing theme key.
7. A wrong entry route or a 403 never logs a valid user out. Logout happens only from the user's own Logout button.

## Preparing future dual-role accounts (not enabled)
Backend today: one `users.role`, checks via `role(u, ...)`. A future dual-role account needs: a `roles` list on `/api/me`, a server-side active role per session, a server endpoint that re-authorises on switch, and rules such as "cannot bid on own request". The shell needs only to render a switcher when the server reports more than one role.

## Known limitations (unchanged from Phase 1 or by design)
- Passenger resume goes to the home map; an in-progress ride is not restored after a reload (was already so).
- A passenger whose profile has no name sees the name screen again at next launch.
- Driver `online` is not cleared server-side on logout (location pings stop; existing behaviour).
- `architecture.md` still describes a Next.js/Supabase target stack; the running code is Node `http` + `node:sqlite` + vanilla HTML.
- Legacy duplicated code (api helper, esc, CSS slicing) is deliberately left until cutover is approved.
